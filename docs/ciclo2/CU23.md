## Alcance y separación de datos

Perfil resumido opcional, alergias y sus revisiones. No incluye diagnósticos,
tratamientos, recetas, resultados, antecedentes detallados, adjuntos, inferencias
clínicas ni recomendaciones automáticas. No transmite datos a terceros.

Reutiliza pacientes sin duplicar nombres, CI o contactos. No reutiliza motivo de
cita ni citas_historial para información clínica. CU04–CU06 y CU11–CU22 conservan
sus reglas, datos y restricciones. Los reportes CU21 y exportadores CU22 siguen
usando sus servicios/consultas originales y no reciben campos clínicos.

Se inspeccionaron MVC, migraciones 001–008, esquema real, vinculación de médicos,
CU14/CU19/CU20, sesiones, CSRF, escape, enrutamiento y fixtures antes de modificar
el código. CU20 permite antecedentes administrativos por citas de cualquier
fecha/estado; esa relación histórica no concede permiso clínico.

## Permisos y política asistencial

Cada lectura o escritura del servicio vuelve a consultar el actor en PostgreSQL:
cuenta activa, rol Médico, registro médico activo vinculado mediante
medicos.usuario_id, paciente activo y una cita propia con inicio en la fecha
actual de America/La_Paz. Solo califican programada, confirmada, presente y
atendida. Cancelada, inasistencia, citas de ayer o de otro día futuro no califican.

La ventana permite preparar la atención del día y completar información hasta
medianoche. Al cambiar la fecha vence el permiso, aunque exista historial.
También vence si una cita que comienza antes de medianoche termina después:
se usa la fecha de inicio, sin ampliar la ventana a otro día. Esta es una
decisión explícita de acceso y una limitación conocida.

No existe acceso clínico excepcional para Administrador. Administrador,
Recepcionista y Paciente reciben 403 incluso por URL directa; el acceso personal
se revisará en CU25. Sin sesión se exige login. Para Médico, paciente inexistente
o fuera de alcance reciben el mismo 404, sin identidad ni valores clínicos.
Se verifica también la pertenencia de cada alergia al paciente y sus revisiones.
No se confía en botones ocultos ni en rol, médico o responsable enviados por el cliente.

La inspección inicial encontró cero médicos activos con una cuenta válida vinculada.
No se crearon cuentas permanentes ni se vincularon registros existentes. Para uso
manual se necesita una cuenta Médico vinculada mediante la gestión de médicos ya
existente y una cita pertinente del día. Las pruebas crean y retiran sus propios
usuarios, médicos y pacientes inventados.

## Modelo de datos 009

`database/migrations/009_perfil_clinico_alergias.sql` crea tres tablas vacías,
sin seed clínico ni alteración de objetos/registros previos. Usa BIGINT y
TIMESTAMPTZ coherentes con el esquema inspeccionado.

### perfiles_clinicos

| Campo | Tipo y propósito |
|---|---|
| paciente_id | BIGINT, PK y FK a pacientes; un perfil por paciente |
| grupo_sanguineo | VARCHAR(3), NULL o un grupo ABO/Rh permitido |
| fuente_grupo_sanguineo | VARCHAR(120), referencia documental breve |
| observaciones | VARCHAR(500), opcional |
| estado_alergias | VARCHAR(20): no_registrado, sin_conocidas, con_registros |
| version | INTEGER positivo; control de edición concurrente |
| creado_por_usuario_id / actualizado_por_usuario_id | BIGINT, dos FK a usuarios |
| creado_en / actualizado_en | TIMESTAMPTZ |

Un grupo presente exige referencia documental no vacía. Si se desconoce, ambos
son NULL; no se asigna grupo por defecto ni se infiere por datos administrativos.
La referencia recoge la fuente que el médico afirma haber revisado: el sistema
no verifica un documento externo ni permite adjuntarlo.

El perfil conserva creador, último editor, fechas y versión; no conserva una
tabla de todas sus imágenes históricas. No se promete reconstruir los valores
anteriores de cada edición del perfil. La interfaz identifica el último guardado,
sin atribuir una certificación médica automática a los valores.

### alergias_paciente

| Campo | Tipo y propósito |
|---|---|
| id | BIGINT GENERATED ALWAYS AS IDENTITY, PK |
| paciente_id | BIGINT, FK a pacientes |
| sustancia | VARCHAR(120), obligatoria, espacios normalizados |
| reaccion | VARCHAR(250), opcional |
| observaciones | VARCHAR(500), opcional |
| estado | VARCHAR(10): activa, inactiva |
| version | INTEGER positivo |
| creado_por_usuario_id / actualizado_por_usuario_id | BIGINT, dos FK a usuarios |
| creado_en / actualizado_en | TIMESTAMPTZ |

Índice único parcial por paciente y sustancia normalizada solo cuando está activa.
Ignora mayúsculas/espacios repetidos, conserva acentos y no interpreta sinónimos
ni equivalencias médicas. Permite conservar antecedentes inactivos equivalentes.
Otro índice (paciente_id, estado, id) sirve al listado de ambos estados.

### alergias_historial

| Campo | Tipo y propósito |
|---|---|
| id | BIGINT GENERATED ALWAYS AS IDENTITY, PK |
| alergia_id | BIGINT, FK a alergias_paciente |
| version | INTEGER, único junto con alergia_id |
| evento | VARCHAR(20): registro, actualizacion, inactivacion, reactivacion |
| sustancia / reaccion / observaciones / estado | Imagen posterior de la versión, mismos tipos/límites |
| motivo_cambio | VARCHAR(250), obligatorio salvo en el registro inicial |
| usuario_id | BIGINT, FK al responsable |
| cambiado_en | TIMESTAMPTZ |

Cada revisión conserva la imagen posterior, incluida la versión inicial. Rectificar
exige motivo y añade versión; no reescribe imágenes anteriores. Inactivar no
equivale a afirmar que la alergia se resolvió. Reactivar requiere confirmación y
vuelve a comprobar unicidad activa. No hay DELETE ni edición directa del historial
en la aplicación. La bitácora no es inmutable frente al propietario SQL; los
servicios no pueden proteger frente a cambios manuales de ese propietario.

### Integridad y cantidades

Tres tablas, 32 columnas, ocho FK nuevas, 18 CHECK y seis índices contando PK y
UNICIDAD. Las FK son tres del perfil (paciente/creador/editor), tres de alergia
(paciente/creador/editor) y dos del historial (alergia/usuario), todas nuevas con
ON DELETE RESTRICT. El total local pasa de **9 tablas/12 FK a 12 tablas/20 FK**.
No se modifican las ocho tablas originales, citas_historial, GiST, estados,
triggers, catálogos ni las migraciones 001–008.

## Qué significa la información sobre alergias

- Sin perfil o no_registrado: información desconocida; no confirma ausencia.
- sin_conocidas: declaración expresa del médico, con confirmación obligatoria.
- con_registros: antecedentes registrados, diferenciando entradas activas e inactivas.

Una entrada activa impide guardar sin_conocidas/no_registrado. Agregar o reactivar
establece con_registros en la misma transacción. Inactivar la última no declara
ausencia automáticamente: mantiene antecedentes sin entradas activas.
Posteriormente el médico puede declarar sin_conocidas de forma expresa, sin
eliminar las revisiones. Las reglas entre tablas se serializan en el servicio;
no se atribuye a un CHECK una comprobación entre filas que no realiza.

## Rutas e interfaz

| Método y ruta | Operación |
|---|---|
| GET /pacientes/{id}/perfil-clinico | Perfil, estado desconocido y formulario |
| POST /pacientes/{id}/perfil-clinico | Registrar/actualizar con versión esperada |
| GET /pacientes/{id}/alergias | Listado y formulario de alta |
| POST /pacientes/{id}/alergias | Registrar una alergia |
| GET /pacientes/{id}/alergias/{alergia}/editar | Formulario de rectificación/estado |
| POST /pacientes/{id}/alergias/{alergia}/actualizar | Guardar revisión con motivo y versión |
| GET /pacientes/{id}/alergias/{alergia}/historial | Revisiones autorizadas |

IDs enteros positivos y control de desbordamiento. Escrituras solo por POST con
CSRF y confirmación obligatoria; POST-Redirect-GET después de guardar. No se
ponen valores clínicos en URL, cookies, mensajes flash o sesiones. Un formulario
inválido se renderiza en la respuesta privada, escapado y acotado; conserva la
versión antigua para impedir sobrescribir una edición ajena sin recargar.

La agenda ofrece el enlace solo al médico con relación pertinente. Su proyección
añade el ID del paciente, sin detalles clínicos. Un conjunto de IDs autorizado
se obtiene en una consulta acotada al día y se revalida al abrir CU23. La agenda
administrativa no ofrece acceso clínico y sus filtros/reglas no cambian.
Las vistas usan estilos locales responsivos y formularios breves; no se generan
capturas clínicas durante las pruebas.

## Bloqueos, transacciones y privacidad

READ COMMITTED, médico antes que paciente/cita, en coordinación con CU11–CU18.
Lecturas usan FOR SHARE, escrituras bloquean el médico y paciente con FOR UPDATE.
El paciente serializa a distintos médicos autorizados que editan su información.
Se bloquea la cuenta para mantener su rol/actividad durante la operación.
La fecha de la cita se comprueba de nuevo después de esperar y antes de confirmar.

Perfil, alergia y revisión se guardan juntos o se revierten juntos. Se compara
versión esperada, el índice cubre duplicados concurrentes, los conflictos devuelven
409 y los errores inesperados 503 con mensajes fijos. En una transacción del
llamador se usa SAVEPOINT, sin confirmar ni revertir sus cambios ajenos.

PDO parametrizado; UTF-8, tipos, longitudes y controles se validan en el servidor.
Los espacios, incluidos saltos de línea aceptados, se normalizan a un espacio.
Los límites son grupo 3, fuente/sustancia 120, reacción/motivo 250, observaciones
500 caracteres. Las vistas escapan con e(). Las páginas envían Cache-Control
private/no-store, Pragma no-cache y conservan CSP, autenticación, sesiones y CSRF.
Formularios con autocomplete off, sin garantía sobre preferencias externas del navegador.
Las excepciones públicas no contienen datos ni arrastran excepciones PDO nativas.
No hay valores clínicos en logs, reportes, exportaciones, capturas o archivos públicos.

La autorización del usuario precedió a la ejecución. El asistente
`scripts/aplicar-migracion-009.php` exige --autorizado, CLI y Cu15Local antes de
conectar: host loopback, nombre exacto y PostgreSQL 17. Dentro de una transacción,
bloqueó la migración y las nueve tablas previas, validó 001–008 y ausencia de 009,
aplicó todo el SQL, comprobó las tres tablas vacías y comparó huellas de registros,
columnas, restricciones, índices y triggers previos antes de COMMIT.
Cualquier error habría revertido toda la transacción, sin reintentos.

**009 ya está aplicada: no repetir el asistente ni volver a inicializar la base.**
El inspector previo `scripts/inspeccionar-cu23-local.php` es solo para una base
anterior a 009 y ahora la rechaza intencionalmente. Comandos actuales READ ONLY:

```powershell
php scripts/verificar-cu23-local.php
php scripts/verificar-cu15-local.php
php scripts/inspeccionar-cu18-local.php
php tests/esquema_cu23_validation.php
```

El verificador SQL valida el catálogo clínico completo contra metadatos del SQL
aprobado aplicado a PostgreSQL 17, incluidos valores predeterminados, CHECK, FK,
PK y definición/validez de índices. Solo después proyecta las nueve tablas
administrativas y aplica su contrato previo. Rechaza instalaciones parciales,
columnas extras, restricciones debilitadas o tablas imprevistas, sin aceptar solo
cantidades. Mantiene 8/10 y 9/12; los estados previos se prueban con metadatos
aislados en memoria, sin crear otras bases ni deshacer migraciones.
